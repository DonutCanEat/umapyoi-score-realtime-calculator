# 影像辨識設計（Phase 1）

> 關鍵前提（用戶確認 + 實測）：**賽馬娘桌面版嘅解析度唔固定，只有比例固定。**

## 0. 實測證據

用你提供嘅截圖（1902 × 1101）逐行掃描平均色：

| 區域 | 像素範圍 | 內容 |
|---|---|---|
| 標題列 | y = 0 ~ 30 | 統一淺灰 `(246,241,244)` |
| 遊戲客戶區 | y = 31 ~ 1101 | 開始出現彩色內容 |

- 客戶區 ≈ **1900 × 1070 → 1.7776 ≒ 16:9**（16:9 = 1.7778）
- 標題列 31px 係**固定像素**，唔會跟比例縮放

**結論**：任何用「視窗矩形」或者「絕對像素」做基準嘅座標都會漂。設計必須用**相對座標 + 相似變換**。

## 1. 座標模型

每個 ROI 一律存成相對值，而且係相對於**遊戲內嘅錨點**，唔係相對於視窗或者螢幕：

```jsonc
// profile.json
{
  "anchor": { "id": "statPanel", "referenceBox": [292, 700, 615, 92] },
  "rois": {
    "speed":   { "x": 0.008, "y": 0.42, "w": 0.155, "h": 0.30 },
    "stamina": { "x": 0.172, "y": 0.42, "w": 0.155, "h": 0.30 }
    // ...
  }
}
```

執行時（每一幀都重新計）：

```js
const scaleX = anchorPx.w / anchorRef.w;   // 等比縮放 ⇒ scaleX === scaleY
const scaleY = anchorPx.h / anchorRef.h;
const roiPx = {
  x: anchorPx.x + roi.x * anchorPx.w,
  y: anchorPx.y + roi.y * anchorPx.h,
  w: roi.w * anchorPx.w,
  h: roi.h * anchorPx.h,
};
```

因為 UI 係**等比縮放**，`scaleX === scaleY`，所以呢個係精確嘅相似變換（scale + translate），
唔會有 aspect 誤差。視窗移動、改大小、最大化、DPI 改變都自動食得住。

### 為何唔用視窗矩形做基準

1. Electron 冇「其他程式視窗 bounds」嘅 API，要 Win32 P/Invoke，多一層依賴。
2. 視窗矩形包含**固定像素高嘅標題列**（實測 31px）→ 垂直方向一定會漂。
3. 全螢幕 / 無邊框 / 唔同 DPI 之下 non-client area 計法都唔同。

### 為何唔用「整個畫面」做基準

letterbox 黑邊同桌面縮放會令比例失真。

## 2. 錨點策略

> ⚠️ **2026-09 修正：以下「靠飽和色／粉紅標題列」嘅方案已經**放棄**。**
>
> 原因（兩層）：
> 1. 用戶實機確認：**ステータス面板顏色係跟隻馬嘅主題色**，唔一定粉紅 →
>    任何寫死色相嘅判定都會喺其他馬身上失效。
> 2. 更根本：**唔可以只用顏色判「數字墨」**。遊戲插畫係一大片暖色調，
>    大量像素啱啱好落喺「橙棕 + 偏暗」窗口。實測 `shots/reference.png`：
>    原始墨點 67,917 粒，最長一條「文字行」係 y=400..939（**高 540 行**）、
>    墨點 48,372 粒 —— 即係成幅插畫被當成一行文字，於是「按墨量揀行」永遠揀錯。
>
> **正解（現行實作）**：見下面 §2.1。

### 2.1 現行做法：唔靠顏色，直接捉「五個數字」嘅結構

```
buildInkMask()      顏色（橙棕、偏暗）＋ 結構（**深色字要喺淺色底上面**）
                    → 用積分圖查 13×13 窗口嘅淺色比例（色彩無關）
                    → 67,917 → 22,125 粒，插畫整條消失
findTextLines()     連續有足夠墨點嘅行 = 文字行
denseBands()        行內再切密集帶（兩行黏埋時分開）
tightenBand()       收窄到真正字身範圍（以峰值 0.25 為門檻、揀墨量最多嘅連續段）
groupsToNumbers()   固定 10px 門檻砌返「數字」（數字內部 2–7px、格與格 28–68px）
pickBestFive()      揀最似五維嘅 5 個（寬度相近、等距）
scoreNumberRow()    結構評分 ＋ coverage（5 個數字要佔盡該行墨量）
extractGlyphs()     切字元 → 縮去 16×24 網格（尺度不變）
readNumberTrimmed() 由右邊貪心收（自動剔走ランク徽章／雜訊）→ 數字
```

**實測結果**：uma1／uma3／uma4 三條培育紀錄 **30/30 格完全命中**真值，
每個字元嘅模板相似度 0.78~0.96。

**唔再需要「相對錨點嘅 ROI 比例」**：因為係直接搵數字本身，
唔靠面板位置；視窗大細、DPI、面板顏色改變都自動食得住。
（原本 §1 嘅相對座標模型仍然係正確嘅原理，只係實作上唔需要預先量度。）

### 2.2 貴重嘅副產品：ランク徽章係最大嘅干擾源

每個屬性格左邊都有ランク徽章。**徽章會唔會被墨點遮罩收錄，係跟主題色**
（實測 uma1 冇、uma2/uma3 有）→ 所以**唔可以假設「每格字元數 = 數字位數」**。
正解：`readNumberTrimmed()` 由右邊貪心收（數字右對齊），遇到低分字元就停。

⚠️ 唔可以用「揀令最差分數最高嘅後綴」：模板係平均值，同一串數字總有啲字元分數低啲，
掉走最弱嗰個一定令最差分數上升 → 「1840」會讀成「40」（實測過）。

#### 2.2.1 實測色相規律（2026-09，`node tools/diag-hue.js --assert`，8 張實機圖 40 格）

| 量度對象 | 色相 | 亮度 | 結論 |
|---|---|---|---|
| **數字墨**（數字框內過判準嘅像素）| p5..p95 = **25..26°**（min 25、max 41–44）| p5..p95 = 0.32..0.59 | 窗口 15–50° 兩邊都有大量餘量 |
| **ランク徽章**（數字框左 3–46px）| **17–44°**（uma1 34–43、uma2 18–43、uma3 34–44、uma4 17–27）| 0.34–0.60 | ⚠️ **同數字墨重疊** |

**規律 1（最重要）**：ランク徽章嘅色相**落喺數字墨窗口入面**，所以
**唔可以靠色相剔徽章** —— 徽章係靠「深色字喺淺色底上面」呢個**結構條件**剔除嘅
（徽章坐喺主題色漸變底上面，窗口淺色比例唔夠）。
實測真正入到遮罩嘅徽章殘墨：uma1 16、uma2 84、uma3 35、uma4 48 粒（散落嘅碎邊，
唔會砌成一個「數字」）。若果結構條件失效，呢個數字會暴增 → `diag-hue.js --assert` 會擋。

**規律 2**：色相窗口嘅作用係**搵行**（detection），唔係執靚讀數。
`tools/tune-detect.js --hue` 單軸掃描（8 張圖，30/40 格係真值命中，
另外 10 格係 uma2 —— 見地雷 #19）：

| 門檻 | 安全範圍（實測） | 現行 | 爆邊嘅表現 |
|---|---|---|---|
| `hueMin` | 0–25° | 15 | 27° → **偵測 0/8 張**（真數字墨係 25°）|
| `hueMax` | 35–90° | 50 | 收窄到 35° 都仲得，冇明顯上界 |
| `lumMax` | 0.50–0.70 | 0.62 | 0.45 → 6/8 張、讀中 6/30；0.85 → 6/8 張、讀中 20/30 |
| `deltaMin` | 0–60 | 30 | 好穩健（結構條件做主力）|
| **色相／亮度全開** | — | — | **偵測 2/8 張**（暖色插畫即刻淹沒）|

→ 即係：**色相窗口係「行偵測」嘅命脈**，但喺 15–50°／0.62 附近好闊嘅範圍內都一樣準。
改動呢幾個值之前，一定要跑 `node tools/tune-detect.js --hue` 睇安全範圍。

#### 2.2.3 實機量測：UI 等比縮放、相對位置穩定，但**讀錯欄**（2026-09-18）

> 內容區一律 16:9），放喺 `shots/live/`。

**量測 1：UI 完全等比縮放 + 面板相對位置穩定**

|---|---|---|---|---|---|
| 1356 | 763 | 558..566 | 0.691–0.701 | 67 | 0.0494 |
| 1748 | 983 | 711..721 | 0.692–0.702 | 87 | 0.0498 |

→ pitch ÷ 圖闊 **恆定 0.0495**、面板 normalized y **恆定 0.691–0.703**。
即係：**寫死「相對座標 ROI」喺固定 16:9 之下係安全嘅**（同 §2.2 嗰個「寫死色相」完全兩回事），
而且**字高 ∝ 圖闊**（實機量到：大數值 ≈ 0.0098×闊、`/上限` ≈ 0.0064×闊）
→ 正確做法係「正規化字高」，唔係「揀一個固定解析度」。

**量測 2：現行判準喺實機主畫面讀錯欄（嚴重）**

實機**育成主畫面**每個屬性格係「**大數值（上）＋ `/上限`（下，細字）**」。
現行判準係「揀 5 個**闊度最相近**嘅等距數字」→ 上限全部 4 位、闊度一致，
數值係 2–3 位、闊度唔一致 → **一定揀到上限欄**：

| 圖 | 現行讀出 | 真值 |
|---|---|---|
| 1356 | ❌ 第 1 個數字讀唔清 | `226/54/139/85/102` |
| 1748 | ❌ `1946/1600/1600/1500/1450`（＝上限）| 同上 |
| 2032 | ❌ `1948/0/0/1500/1450` | 同上 |
| 2367 | ❌ `1948/1000/1800/1500/1450` | 同上 |
| 2560 | ❌ `8/1600/1000/1500/1450` | 同上 |

**5/5 解析度都錯**，而且信心仲有 0.55–0.70 → **靜默報錯數**（HUD 會顯示錯嘅五維分）。
而且 band 會把「大數值行 + 細上限行」**合併**成一條，砌數字時混行，連上限都讀唔準。

**根因**：`pickBestFive()` 嘅「闊度相近 + 等距」判準只喺「5 個數字位數一樣」嘅情況下成立。
gt 截圖（2.2.1 之前一直用嚟驗證嘅 `shots/gt/*`）**係另一種排法**（5 個 4 位數字一行）
→ 所以 gt 30/30 **唔代表實機行得通**（呢個係地雷 #23）。

**修法（✅ 2026-09-18 已實作，`src/vision/statbar.js`）**：
1. 用**相對 ROI**（實測穩定：x 0.15–0.44、y 0.645–0.735）框住面板條 → 順便解決頻寬問題；
2. ROI 內**先切兩行**（大數值 / 細上限）→ 只讀大數值行；
3. 像素門檻**按字高比例縮放**（切字群 3px、砌數字 10px、窗口半徑 6）—— ⚠️ **唔可以重採樣**：
   試過把 24px 嘅字縮到 17px，筆劃變薄、反鋸齒令像素變淺 → 遮罩穿窿 → 一個「6」切成兩橛；
   正解係喺原生解析度做遮罩，靠 `extractGlyphs()` 嘅逐字元 16×24 正規化處理尺度；
4. ⚠️ **遮罩要喺整個 ROI 做**，唔可以剪一條貼邊條帶：條帶冇淺色底 →
   「深色字喺淺色底」失效 → 有環嘅數字（6/8/9）筆劃被剔走、碎裂；
5. 揀 5 個數字只按**右邊界間距**（`pickFiveBySpacing()`）—— 實機數值喺格內**右對齊**，
   所以 x0 間距會跟位數交替（105/76/103/77），x1 間距先係等距（90/90/90/89）；
6. 加**信心閘**（`minConfidence`）—— 寧願顯示「讀唔到」，唔可以顯示錯數。

**實測結果**：`shots/live/` 1356→2560 五個解析度 **5/5 全中**（信心 0.80–0.89）；
模板改用「面板截圖 ＋ 實機面板條」一齊訓練（雙閘：面板截圖 30/30、實機面板條 5/5）；
擷取端改為 renderer **1:1 剪面板 ROI** 先傳（~0.5MB/幀，順手解埋 §2.2.2）。

## 3. 字元辨識：尺度不變嘅模板比對

> ✅ 呢一節嘅原理**已實作並驗證**（30/30）。實作位置：
> `src/vision/glyphs.js`（切字、歸一化、NCC）＋ `tools/build-glyph-templates.js`（建模板）。

**唔可以**用原始像素做模板，因為每個解析度下字都唔同大細。流程：

1. ROI → 背景受控墨點遮罩（見 §2.1；唔係單純二值化，要「深色字喺淺色底」）
2. 欄投影 → 切出每個字元（字距門檻 1 欄：反鋸齒會令字黏埋）
3. **每個字元正規化**：crop bounding box → resize 去固定網格 **16 × 24**（面積採樣）
4. 去均值 + L2 歸一化 → 同模板做 NCC（等同 cosine 相似度）→ 取最高分
5. **模板由實機截圖自動產生**（唔需要人手標籤）：用 ground truth 做標籤
   → `node tools/build-glyph-templates.js`
6. **幀間多數投票**（視窗 5 幀、過半數 3）＋ 數值合理性檢查：
   - `0 ≤ 值 ≤ 2600`
   - 同一畫面五個值唔應該跳變
   - 五維只會單調上升（育成期間只加唔減），跌就當讀錯
     —— 但**整個窗口都一致咁跌**就當係真變化（事件扣屬性），唔會卡死

> ⚠️ **模板驗證一定要有硬閘**。舊版會靜靜哋用一列錯嘅字建立模板，
> 而驗證步驟又比錯嘢（用「全部字元」比「真值位數」）→ 一路冇人發現模板係垃圾
> （讀任何字嘅相似度都得 0.07~0.6）。
> 而家 `build-glyph-templates.js` **驗證唔到 100% 就唔寫檔**，並且會列出失敗明細。

## 4. 自動偵測（**唔需要手動框選**）

> ⚠️ 用戶明確要求：**即時偵測**，唔係「開程式 → 拉框 → 確認」嗰種手動校準。
> 所以以下全部自動，用戶只需要照玩。

### 4.1 零校準：唔需要參考 profile

> ⛔ 舊方案（由截圖量出參考座標、內建成 profile）**已放棄** ——
> 因為根本唔需要座標模型（見 §2.1）。直接喺圖上捉「五個數字」就得。

之前提過嘅「內建 `statsRoi` 相對錨點」已經冇用。現時只有兩樣要「預先準備」：

```jsonc
// data/glyph-templates.json（由 tools/build-glyph-templates.js 自動產生）
{
  "grid": [16, 24],          // 歸一化網格
  "digits": "0123456789",
  "sources": 6,              // 用咗幾多張截圖訓練
  "templates": { "0": [...], "1": [...] }   // 每個數字嘅平均字形
}
```

**字形模板一樣自動產生**：用 ground truth JSON 做標籤（我哋已經知道每張圖嘅真值），
切字 → 對號入座 → 平均 → 10 個數字。
⚠️ 但一定要有**驗證閘**：驗證唔到 100% 就唔寫檔（見 §3 尾）。

### 4.2 執行時流程（全自動，**已實作**）

1. 啟動即開始循環擷取遊戲視窗
2. 每幀：擷取 → 縮圖（640px）→ 傳 raw RGBA 入 Node 主程序
3. Node 側：`readStats()`（背景受控墨點 → 文字行／密集帶 → 5 個數字 → 切字 → 模板比對）
4. 幀間多數投票（`StatTracker`）→ 穩定先出數 → `evaluate()` 算評價分
5. 讀唔到（轉場／唔喺ステータス畫面）→ **唔出數**，HUD 唔好亂估

用戶完全唔需要設定。

### `／NNNN` = 屬性上限

實測數據亦支持：1914 / 1609 / 1600 / 1500 / 1466 對屬性值 169 / 103 / 128 / 105 / 92 **唔單調**
